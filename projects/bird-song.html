Bird Song Synthesizer ASM

Program the development board so its buzzer imitates four real bird calls. Pitch is generated with a timer interrupt, note lengths with a second timer, and each call is stored as data in program memory.

Requirements

Your program must meet all of the following. The demo and grading are based on this list.

#Requirement
R1Pressing K1, K2, K3 or K4 plays bird call 1, 2, 3 or 4 (below) once.
R2The matching LED (D1–D4) is on while its call plays and off otherwise.
R3Holding a button does not repeat the call. The button must be released and pressed again.
R4The tone is a square wave on the buzzer pin generated by the Timer 0 interrupt. No software delay loops for pitch.
R5Note durations are timed with Timer 1 using a 5 ms time base (polled or interrupt-driven).
R6Each call is stored as a data table in program memory and played by one shared routine, not as a separate block of code per bird.
R7When no call is playing, the buzzer is silent and its pin is left HIGH.
R8Measured pitch is within ±3% of the specification. Check it with a tuner or spectrogram app on your phone.

Pin assignments are on the pin map. This project uses the buzzer on P2.5, K1–K4 on P3.1, P3.0, P3.2, P3.3 and D1–D4 on P2.0–P2.3. Remove the LCD module during this project, because it shares P2.5. LED D6 is also on P2.5, so it glows faintly while a call plays. That is normal.

How a sweep is defined

A sweep from f1 to f2 lasting T in steps of s has n = T / s notes, each held for s. Note i (0 … n−1) has frequency

fi = f1 + (f2 − f1) × c(u),   u = i / (n − 1)
Curvec(u)Shape
linearuConstant rate of change
fast1 − (1 − u)²Changes quickly at first, then levels off, like a whistled slur
slowu²Starts slowly and changes quickly at the end

The first note is exactly f1 and the last exactly f2. The tables have many notes, so it is sensible to calculate them with a spreadsheet or a short script. Include it with your submission.

Background

Making a pitch with a passive buzzer

A passive buzzer only sounds while its drive signal keeps changing. Toggling the pin every half period produces a square wave, so a tone of frequency f needs a toggle every T/2 = 1/(2f) seconds. On this board the buzzer is driven through a PNP transistor.

Timer 0 in mode 1

With the 11.0592 MHz crystal in 12T mode, a timer counts 921 600 times per second. In mode 1 it counts up from the value you load into TH0:TL0 and sets TF0 (and requests an interrupt) when it rolls over from FFFFH to 0000H. To overflow after N counts, load:

reload = 65536 − N

Example: a 3000 Hz tone has a half period of 1/6000 s = 153.6 → 154 counts, so reload = 65536 − 154 = 65382 = FF66H.

Mode 1 does not reload itself, so your ISR must reload the timer on every overflow. The interrupt response and the reload take some time, and those counts add to every half period. Expect the measured pitch to be slightly lower than calculated, most of all at high frequencies. Measure it and correct for it to meet R8.

More detail: Wiki: Timers · Wiki: Interrupts · Wiki: Clock & timing.

A 5 ms time base with Timer 1

Every note in the specification is a whole number of 5 ms steps. Use Timer 1 to measure exactly 5 ms, and count those steps to hold each note for its length. Work out the reload value yourself and verify it (see Milestone 1).

Storing sounds as tables

R6 asks you to describe each call as data rather than code. A simple format is a list of notes, each giving a pitch and a length, with special values for a rest and for the end of the call:

CALL_NAME:
    DB  pitch_high, pitch_low, length   ; one note
    DB  ...                             ; more notes
    DB  <rest code>, length             ; silence
    DB  <end marker>                    ; end of the call

Choose your own encoding for pitch, rest and end, and document it in your code. A sweep is a sequence of short notes. Tables are read with MOVC A,@A+DPTR, as in the 7-segment example.

Design notes

How you structure the program is up to you. These are points to consider while designing it, not a required structure:

  • Division of work. The ISR should do as little as possible: reload and toggle. Reading tables, timing notes and checking buttons belong in the main program.
  • Shared data. The main program chooses the pitch and the ISR uses it. What happens if the interrupt fires halfway through updating a 16-bit value?
  • Starting and stopping the tone. Think about what state the timer, its flag and the buzzer pin are left in when a note ends, a rest starts or a call finishes (R7).
  • Register usage. If the ISR uses A, PSW or R0–R7, the main program's values must be preserved.
  • Buttons. Mechanical buttons bounce for a few milliseconds when pressed and released. R3 also needs you to detect a new press, not just a held button.
  • Stack. After reset SP = 07H. Consider where your stack and RAM variables live (Wiki: Memory).

The starter template gives the pin names, vector addresses, and headings for the routines most solutions need. You may change it freely.

Milestones

Show each milestone to the lab instructor as you reach it.

  1. Time base. Using only your Timer 1 routine, blink LED D8 (P2.7) at 1 Hz (500 ms on, 500 ms off). Ten blinks must take 10 s ± 0.2 s by stopwatch.
  2. Interrupt tone. While K1 is held, the buzzer plays a steady 3000 Hz tone generated by the Timer 0 interrupt. It is silent otherwise.
  3. First call. K1 plays the house sparrow call from a table, with D1 lit.
  4. Complete system. All four calls meet R1–R8.

Bonus (up to +10)

  • Dawn chorus: pressing K1 and K4 together plays all four calls in sequence.
  • Your own bird: design a fifth call that imitates a real bird recording (e.g. from xeno-canto), and play it from a key on the 4×4 keypad. Include the recording link and your specification.
  • Spectrogram: include a phone spectrogram (for example Spectroid on Android) of each call next to the plots on this page, and comment on the differences.

Report questions

Answer in your report and show your working.

  1. Calculate TH0 and TL0 for a 2500 Hz tone, before any correction.
  2. What values did you load into TH1 and TL1 for the 5 ms time base? Show the calculation.
  3. R7 requires the buzzer pin to be left HIGH when idle. Using the buzzer's drive circuit, explain why.
  4. Before correction, what frequency did you measure for the 3000 Hz tone of Milestone 2? What causes the error, how did you correct it, and what was the result?
  5. Your main program and ISR share data. Describe what could go wrong if an interrupt occurs while that data is being updated, and how your code prevents it.
  6. What is the highest frequency your design could produce, and what limits it?
