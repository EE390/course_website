Requirements

R1–R8 are the same as in Mini Project 2. R4 and R6 now apply to C code, and R9 is new.

#Requirement
R1Pressing K1, K2, K3 or K4 plays bird call 1, 2, 3 or 4 (below) once.
R2The matching LED (D1–D4) is on while its call plays and off otherwise.
R3Holding a button does not repeat the call. The button must be released and pressed again.
R4The tone is a square wave on the buzzer pin generated by a Timer 0 interrupt routine written in C (__interrupt(1)). No delay loops for pitch.
R5Note durations are timed with Timer 1 using a 5 ms time base (polled or interrupt-driven).
R6Each call is stored as a data table and played by one shared function, not as separate code per bird.
R7When no call is playing, the buzzer is silent and its pin is left HIGH.
R8Measured pitch is within ±3% of the specification. Check it with a tuner or spectrogram app.
R9The whole program is written in C (no inline assembly), and the sound tables are stored in flash, not RAM. Show this with your .mem / .map files.

Pins are as in Mini Project 2: buzzer P2_5, K1–K4 P3_1, P3_0, P3_2, P3_3, and D1–D4 P2_0–P2_3 (SDCC names). Remove the LCD module. LED D6 glows while a call plays.

How a sweep is defined

A sweep from f1 to f2 lasting T in steps of s has n = T / s notes, each held for s. Note i (0 … n−1) has frequency

fi = f1 + (f2 − f1) × c(u),   u = i / (n − 1)
Curvec(u)Shape
linearuConstant rate of change
fast1 − (1 − u)²Changes quickly at first, then levels off, like a whistled slur
slowu²Starts slowly and changes quickly at the end

The first note is exactly f1 and the last exactly f2. You may reuse the spreadsheet or script from Mini Project 2 and make it output C array initialisers.

Background: C on the 8051

The timer theory is unchanged from Mini Project 2: 921 600 counts per second, reload = 65536 − N, the ISR reloads the timer and toggles the pin, and the measured pitch comes out slightly low until you correct for the ISR's delay. What's new is how you express it in C, and what the compiler makes of it.

Pins and registers

Include <8052.h> and use the register names directly: TMOD = 0x11; TR0 = 1; BUZZER = !BUZZER; with #define BUZZER P2_5. See Wiki: C with SDCC.

Interrupt routines

void timer0_isr(void) __interrupt(1);    /* prototype - must be in the file with main() */

void timer0_isr(void) __interrupt(1)
{
    /* your code: as short as possible */
}

What SDCC generates depends on what you write inside. A routine that only reads and writes SFRs and global variables compiles to plain instructions. If it calls a function, SDCC saves and restores 15 registers on every interrupt. Look at the .rst listing to see exactly what you got (Wiki: Interrupts in C).

Data shared with the ISR

Declare variables used by both main() and the ISR as volatile. If a value takes more than one byte to update, the ISR must not run halfway through the update: use EA = 0; … EA = 1; or __critical { … }.

Tables in flash

The chip has only 512 bytes of RAM, and the four calls need about 1 KB of table data, so the tables must live in flash:

const unsigned char BIRD1[] = { /* your encoding */ };

void play_call(const unsigned char *call)   /* walk through a table with a pointer */
{
    …
}

Choose and document your own encoding, as in Mini Project 2. After building, check the .map file: the tables should be listed with a C: (code) address.

Timing

Don't use empty loops for delays in C: their length depends on the compiler. Use Timer 1 exactly as in Mini Project 2. Also expect each 5 ms tick to come out slightly longer than in assembly, because the function call and loop code add a little overhead.

Design notes

How you structure the program is up to you. Things to consider:

  • Keep the ISR tiny. Reload and toggle, nothing else. Read the .rst listing to confirm SDCC didn't add register saving.
  • Shared data. Which variables do main() and the ISR share, and how do you update them safely?
  • Types. Use unsigned char wherever values fit in 0–255. It's faster and smaller than int.
  • Starting and stopping the tone. What state are the timer, its flag and the buzzer pin in after a rest or at the end of a call (R7)?
  • Buttons. Debounce, and detect a new press (R3).
  • Memory. Watch the RAM and flash totals in the .mem file as your program grows.

The starter template gives pin names, the ISR declaration and suggested function headings. It compiles as it is, but does nothing yet.

Milestones

Show each milestone to the lab instructor as you reach it.

  1. Toolchain and time base. Build with SDCC and program the board. Using only your Timer 1 function, blink LED D8 (P2_7) at 1 Hz: 10 blinks in 10 s ± 0.2 s.
  2. Interrupt tone in C. While K1 is held, a steady 3000 Hz tone is generated by your C interrupt routine. It is silent otherwise.
  3. First call. K1 plays the Bird 1 call from a table in flash, with D1 lit.
  4. Complete system. All four calls meet R1–R9.

Bonus (up to +10)

  • Serial control: typing 1–4 in a serial terminal (9600 baud) plays the matching call, and the board replies with the call's name.
  • Your own bird: add a fifth call imitating a real recording, played from the 4×4 keypad.
  • Size challenge: make your C build no more than 10% larger than your assembly build, and explain what you changed.

Report questions

Answer in your report. Include listings or file excerpts where asked.

  1. Using your .map and .mem files: where are your sound tables stored, and how much flash and RAM does your program use? What would happen if the tables were declared without const?
  2. Copy the assembly SDCC generated for your Timer 0 ISR (from the .rst file). Which registers does it save, if any? Compare it with the ISR you wrote by hand in Mini Project 2.
  3. Measure the 3000 Hz tone of Milestone 2 before correction. Is the error the same as in Mini Project 2? Explain using your answer to question 2.
  4. Change your ISR so it calls a small function (e.g. toggle_buzzer()). What changes in the generated code and in the measured pitch? Why?
  5. Why must variables shared by main() and the ISR be volatile? Show how your code prevents the ISR from seeing a half-updated value.
  6. Compare your C and assembly versions: code size in bytes, the length of one call as measured, and development time. When would you choose C, and when assembly, for a microcontroller project?
